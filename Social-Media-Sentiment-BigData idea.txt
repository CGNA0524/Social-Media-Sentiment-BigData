1. PROJECT AIM & HIGH-LEVEL VISION
====================================================================================================
The primary aim of this project is to architect, develop, and benchmark an enterprise-grade,
distributed-capable Big Data and Natural Language Processing (NLP) ecosystem that can ingest, clean,
classify, index, stream, and analyze massive volumes of social media conversations in real time.

Specific Strategic Goals:
1. Ingestion at Scale: Successfully ingest, validate, and process massive social media corpora,
   including the 1.6 Million-row Sentiment140 dataset (239 MB), the 14,640-row US Airline Sentiment
   dataset, and relational SQLite dumps without memory overflow (OOM).
2. Intelligent NLP Normalization: Transform noisy, slang-ridden social media micro-posts into clean,
   vectorizable features while strictly preserving critical sentiment signals (specifically negation
   words like "not", "no", "never", and contraction forms).
3. Machine Learning Baseline Benchmarking: Implement and compare classic statistical machine learning
   classifiers (Multinomial Naive Bayes with Laplace smoothing vs. L-BFGS Logistic Regression) under a
   strict, no-leakage scikit-learn Pipeline architecture.
4. Contextual Deep Learning: Upgrade the baseline with state-of-the-art Transformer models (DistilBERT
   and CardiffNLP Twitter-RoBERTa) to capture nuanced syntactic and semantic dependencies.
5. Real-Time Stream Analytics: Build an Apache Flink-inspired event-driven streaming pipeline capable
   of handling micro-bursts of tweets with tumbling window aggregations, watermarking, and throughput
   monitoring.
6. Fast Distributed Search: Deploy Elasticsearch with tailored schema mappings (supporting nested
   aspect objects) to enable sub-second keyword and multi-faceted sentiment search.
7. Automated Big Data Orchestration: Design a robust 7-stage Apache Airflow Directed Acyclic Graph (DAG)
   automating the entire lifecycle from ingestion to audit report generation.
8. Fine-Grained Aspect Mining: Implement Aspect-Based Sentiment Analysis (ABSA) with clause boundary
   segmentation to solve the "mixed sentiment" problem where multiple contrasting opinions coexist in
   the same post.
9. Interactive Dashboard: Provide a modern, dark-themed Streamlit web interface for interactive
   demonstrations, live model benchmarking, MapReduce labs, and comprehensive project defense.

2. PROBLEM STATEMENT & INDUSTRIAL RELEVANCE
====================================================================================================
Social media platforms (such as X/Twitter, Reddit, and Instagram) produce hundreds of millions of
user-generated posts every single day. For corporations, airlines, governments, and brand managers,
understanding consumer sentiment is vital for:
- Brand reputation tracking
- Crisis management and customer churn prevention
- Product defect detection and feature feedback
- Real-time market sentiment analysis

However, analyzing social media text poses fundamental Big Data & NLP challenges:

A. Volume & Velocity (Big Data Constraints):
   Traditional relational databases (RDBMS) like MySQL or PostgreSQL choke when asked to execute
   full-text tokenization and n-gram vectorization across millions of streaming rows in real time.
   They lack native horizontal scaling and parallel map-reduce distributed aggregation primitives.

B. Linguistic Noise & Slang:
   Social media text is notorious for misspellings, excessive punctuation (e.g., "soooo bad!!!!"),
   user mentions (@airline), URLs, and emojis. Standard text cleaners blindly strip everything or
   apply generic stopword filters. Removing "not" from "not good" turns a severely negative tweet into
   a positive "good", completely inverting the classification.

C. The "Mixed Opinion" Blind Spot:
   Consider the sentence: "The camera is excellent, but the battery life is disappointing."
   A standard binary sentiment classifier evaluates the overall text, cancels positive against
   negative signals, and outputs an ambiguous "neutral" score. In reality, the customer loves the
   camera (+1.0) and hates the battery (-1.2). Global classifiers miss actionable product feedback.

D. Architecture Silos:
   Most academic projects either implement a simple Jupyter notebook with a basic model OR a dummy web
   UI. Very few demonstrate an end-to-end production architecture connecting ingestion, cleaning,
   parallel computing, deep learning, stream processing, search indexing, and automated orchestration.

4. HOW THE PROJECT WAS BUILT (STEP-BY-STEP IMPLEMENTATION METHODOLOGY)
====================================================================================================
The project was engineered through a disciplined 10-phase software engineering lifecycle:

Phase 1: Project Environment & Dependency Foundation
- Configured a dedicated Windows Python 3.11.9 virtual environment (`.venv`).
- Audited package compatibility between pandas, scikit-learn, PyTorch, Transformers, and Elasticsearch.
- Maintained a clean configuration template (`.env.example`) and comprehensive `.gitignore`.

Phase 2: Data Ingestion & ETL Engineering (`src/data_processing/load_dataset.py`)
- Built chunked, memory-safe loaders for the 1.6 Million-row Sentiment140 CSV (latin-1 encoding,
  headerless, binary labels 0 and 4).
- Built normalized loaders for the 14,640-row US Airline Tweets CSV (3 classes: neg, neu, pos).
- Built read-only SQLite database connector (`file:database.sqlite?mode=ro`).
- Implemented stratified sampling and automated caching to Parquet format (`data/processed/`).

Phase 3: Negation-Preserving Preprocessing Pipeline (`src/data_processing/preprocess.py`)
- Created regex engines for URL stripping, user mention removal, HTML unescaping, and character de-duplication.
- Expanded conversational contractions ("can't" -> "cannot", "won't" -> "will not").
- Engineered custom stopword filtering that explicitly retains sentiment-bearing negation tokens
  ("not", "no", "never", "cannot", "hardly", "barely").

Phase 4: Baseline Model Training & Benchmarking (`src/models/train.py`, `evaluate.py`, `predict.py`)
- Implemented `TfidfVectorizer` (unigrams + bigrams, sublinear TF scaling, max 25,000 features).
- Bound vectorizer and classifiers inside a scikit-learn `Pipeline` to prevent data leakage.
- Trained and benchmarked Multinomial Naive Bayes (Laplace smoothing alpha=1.0) against Logistic
  Regression (L-BFGS solver).
- Persisted serialized model binaries (`models/*.joblib`) with metadata.

Phase 5: Parallel Big Data Simulation Engine (`src/big_data/`)
- Developed a multi-worker `MapReduceEngine` simulating the true Hadoop/MapReduce architecture:
  Input Splits -> Multi-Threaded Mappers -> Local Combiners -> Shuffle & Sort -> Reducers.
- Created standalone Hadoop Streaming executable scripts (`hadoop_streaming_mapper.py` and
  `hadoop_streaming_reducer.py`) for stdin/stdout piping.
- Integrated a PySpark / Local Vectorized abstraction with execution telemetry.
- Built a NoSQL persistence layer supporting live MongoDB with automatic SQLite/JSON fallback.

Phase 6: Transformer Deep Learning Integration (`src/models/transformer_models.py`)
- Integrated Hugging Face Transformers and CPU-compatible PyTorch.
- Loaded `distilbert-base-uncased-finetuned-sst-2-english` (66M parameters, SST-2 binary sentiment).
- Loaded `cardiffnlp/twitter-roberta-base-sentiment-latest` (125M parameters, trained on 124M tweets).
- Built lazy singleton loading and cache unloading mechanisms to protect RAM.
- Implemented unified multi-model comparison functions.

Phase 7: Fine-Grained Aspect-Based Sentiment Analysis (`src/models/absa_engine.py`)
- Developed a discourse boundary segmenter that splits sentences across contrastive conjunctions
  ("but", "however", "although", "yet", "while").
- Extracted domain opinion targets (compound nouns and entities: camera, battery life, crew, food).
- Computed localized sentiment polarities and synthesized overall sentence sentiment (Mixed, Positive,
  Negative, or Neutral).

Phase 8: Distributed Search & Indexing Engine (`src/search/`)
- Implemented official Elasticsearch client wrapper with environment variable authentication.
- Defined idempotent index schema mapping with nested properties for ABSA results.
- Built bulk indexing services (`helpers.bulk`) and full-text keyword search with multi-match and
  boolean filter queries (sentiment, time range, aspect).
- Created a resilient offline fallback to local JSONL files.

Phase 9: Real-Time Stream Processing (`src/streaming/`)
- Engineered a streaming event generator emitting timestamped tweet records.
- Built a 4-stage stream pipeline: Validation -> Normalization -> Sentiment & ABSA -> Sinks.
- Implemented tumbling event-time window aggregations, real-time throughput metrics (EPS), and
  dispatch to Elasticsearch and JSONL sinks.
- Provided both a verified local simulator and a declarative PyFlink DataStream job specification.

Phase 10: Automated Workflow Orchestration (`src/orchestration/`)
- Developed modular Python callables for 7 pipeline stages.
- Created a standard Apache Airflow DAG (`social_media_sentiment_pipeline.py`) with linear task
  dependencies (`t1 >> t2 >> t3 >> t4 >> t5 >> t6 >> t7`).
- Implemented `AirflowPipelineRunner` allowing full sequential execution and audit logging directly on
  Windows without requiring an active Linux Airflow daemon.

Phase 11: Interactive Presentation Layer & Comprehensive Testing (`app.py`, `tests/`)
- Built an expansive, dark-themed Streamlit web dashboard spanning 13 interactive pages.
- Authored 40 automated unit tests achieving 100% pass rate.
- Committed and pushed the entire production codebase to GitHub.

6. WHY SPECIFIC TECHNOLOGIES WERE CHOSEN & DETAILED COMPARATIVE ANALYSIS
====================================================================================================

----------------------------------------------------------------------------------------------------
6.1. Multinomial Naive Bayes vs. Logistic Regression vs. BERT & RoBERTa
----------------------------------------------------------------------------------------------------
Why multiple models?
In enterprise data science, no single model is best for every scenario. There is always a trade-off
between inference latency, memory consumption, and contextual accuracy.

A. Multinomial Naive Bayes (Baseline):
   - Mechanism: Calculates conditional probability P(Class | Words) using Bayes' Theorem with Laplace
     smoothing (alpha=1.0). Assumes all words are conditionally independent given the class.
   - Pros: Blazing fast training (< 1 second for 50,000 tweets) and ultra-low inference latency (< 1.5 ms).
   - Cons: Cannot understand word order or negations separated from adjectives (e.g., "not really good").
   - Role in Project: Curriculum baseline and ultra-fast real-time streaming filter.

B. Logistic Regression (Comparison):
   - Mechanism: Linear classifier optimizing weights jointly via binary cross-entropy loss (log loss)
     using the L-BFGS solver.
   - Pros: Captures correlations between n-grams (e.g., "not_good" bigram), yielding higher accuracy (77.53%
     vs 76.22%) and better calibrated probabilities (ROC-AUC 0.8566 vs 0.8433).
   - Cons: Still bound to fixed vocabulary; cannot generalize to out-of-vocabulary slang.

C. DistilBERT (Contextual Transformer):
   - Mechanism: 6-layer distilled transformer using self-attention heads trained on BookCorpus and Wikipedia.
   - Pros: Understands syntax and semantics bidirectionally; 40% smaller and 60% faster than full BERT-base.
   - Cons: Higher CPU latency (~25 ms per tweet).
   - Role in Project: Contextual binary sentiment scoring with 99.9% confidence on clean reviews.

D. Twitter RoBERTa (CardiffNLP):
   - Mechanism: 12-layer RoBERTa architecture pre-trained on 124 Million real-world Twitter posts.
   - Pros: Specifically tuned for social media syntax, emojis, hashtags, and informal speech. Supports 3
     genuine classes (negative, neutral, positive).
   - Cons: Largest model checkpoint (~499 MB), ~45 ms latency on CPU.
   - Role in Project: Premium contextual social media analyzer.

----------------------------------------------------------------------------------------------------
6.2. Batch Processing (MapReduce/Spark) vs. Real-Time Streaming (Apache Flink)
----------------------------------------------------------------------------------------------------
- MapReduce & Spark (Batch):
  Designed for bounded, historical datasets (e.g., processing the full 1.6M Sentiment140 corpus). Reads
  from disk, splits across workers, performs heavy aggregations, and writes results. High throughput,
  high latency (seconds to minutes).
- Apache Flink (Streaming):
  Designed for unbounded, live data streams (e.g., live Twitter firehose). Processes records one-by-one
  or in micro-windows as they arrive. Uses event-time watermarking to handle out-of-order data. Low
  latency (milliseconds), continuous throughput.

Why both in our project?
A complete Big Data platform requires the Lambda/Kappa architecture: Spark/MapReduce handles deep
historical model retraining, while Flink processes incoming live tweets and updates sliding window metrics.

----------------------------------------------------------------------------------------------------
6.3. Relational Storage (SQLite) vs. Document Store (MongoDB) vs. Search Engine (Elasticsearch)
----------------------------------------------------------------------------------------------------
- SQLite (RDBMS):
  ACID compliant, relational tabular schema. Ideal for small, structured metadata (e.g., the US Airline
  Tweets database). Unsuitable for high-throughput distributed writes or inverted-index text search.
- MongoDB (NoSQL Document Store):
  Flexible JSON/BSON document schema. Easily stores semi-structured tweet objects with dynamic metadata
  (user profile, geo coordinates, hashtags). High write performance.
- Elasticsearch (Distributed Search Engine):
  Built on Apache Lucene with inverted indices and BM25 relevance scoring. While MongoDB can store
  documents, Elasticsearch excels at fuzzy full-text keyword search, nested object queries (ABSA
  aspect filtering), and real-time faceted aggregations.

----------------------------------------------------------------------------------------------------
6.4. Scheduled Scripts vs. Apache Airflow Workflow Orchestration
----------------------------------------------------------------------------------------------------
- Why not just run a Python script or cron job?
  Ordinary scripts lack:
  * Directed Acyclic Graph (DAG) dependency management (Stage 2 cannot run if Stage 1 fails).
  * Automated retries with exponential backoff on transient network failures.
  * Task-level idempotency and independent re-runability.
  * Visual audit trails, execution duration tracking, and centralized logging.
- Airflow provides a robust, enterprise-grade control plane ensuring every step (Ingest -> Clean ->
  Predict -> ABSA -> Index -> Report) executes reliably with zero data corruption.

Feature 5: Aspect-Based Sentiment Analysis (ABSA)
----------------------------------------------------------------------------------------------------
- Implementation File: `src/models/absa_engine.py`
- Mechanism:
  1. Clause Boundary Segmentation: Uses regex patterns across contrastive discourse markers
     (`but`, `however`, `although`, `yet`, `while`, `on the other hand`) to segment text into opposing clauses.
  2. Opinion Target Extraction: Matches common domain compound entities (`camera`, `battery life`,
     `customer service`, `cabin crew`, `seat comfort`, `flight delay`, `wifi`, `food`).
  3. Contextual Polarity Scoring: Evaluates local sentiment words surrounding the aspect, applying
     negation modifiers (`not`, `never`) and intensifiers (`extremely`, `really`).
  4. Synthesizer: If both positive and negative aspects exist, outputs overall sentiment as **MIXED**.
- Verified Test Case:
  * Text: *"The camera is excellent, but the battery life is disappointing."*
  * Aspect 1: "camera" -> POSITIVE (Confidence: 84.0%, Polarity: +1.0)
  * Aspect 2: "battery life" -> NEGATIVE (Confidence: 85.3%, Polarity: -1.2, Contrasting Clause: True)
  * Synthesized Overall: **MIXED** (2 aspects detected)

   Step 3: User mention stripping (`@\w+` -> `""`).
   Step 4: Hashtag symbol removal with token preservation (`#delay` -> `delay`).
   Step 5: Contraction expansion (`can't` -> `cannot`, `won't` -> `will not`, `n't` -> ` not`).
   Step 6: Lowercasing and non-alphabetic character stripping.
   Step 7: Negation-preserving stopword filtering (`CUSTOM_STOPWORDS = NLTK_STOPWORDS - NEGATION_WORDS`).

14. COMPREHENSIVE VIVA VOCE & TECHNICAL INTERVIEW PREPARATION (15 QUESTIONS & ANSWERS)
====================================================================================================

Q1: What is the main objective of this project?
A1: The main objective is to build an end-to-end Big Data and NLP platform capable of ingesting,
    preprocessing, classifying, indexing, streaming, and orchestrating massive social media datasets
    using both statistical ML (Naive Bayes, Logistic Regression) and modern deep learning (BERT, RoBERTa),
    complemented by Apache Flink, Elasticsearch, and Apache Airflow.

Q2: Why did you choose Sentiment140 and US Airline Tweets?
A2: Sentiment140 provides Big Data scale (1.6 Million rows, 239 MB) with binary labels (0=negative,
    4=positive) to test distributed ingestion, MapReduce, and scalability. The US Airline Tweets dataset
    (14,640 rows) provides real-world domain complexity with 3 classes (negative, neutral, positive) and
    rich metadata (airline, negative reason, flight location).

Q3: Why is negation preservation critical in social media text preprocessing?
A3: Standard stopword lists (like default NLTK) remove words like "not", "no", and "never". In sentiment
    analysis, stripping "not" from "not happy" turns a strongly negative sentence into a positive "happy"
    token, completely inverting the classification. Our preprocessor explicitly preserves negation tokens.

Q4: What is data leakage and how did your architecture prevent it?
A4: Data leakage occurs when test set information inadvertently influences training (e.g., fitting the
    TF-IDF vocabulary across the entire dataset). We prevented it by wrapping the vectorizer and classifier
    inside a strict scikit-learn `Pipeline` that is fit exclusively on `X_train`.

Q5: Why does Logistic Regression slightly outperform Naive Bayes?
A5: Naive Bayes makes a strict "naive" assumption that all words are conditionally independent given the
    class. Logistic Regression jointly optimizes weights using binary cross-entropy loss, allowing it to
    model correlated word pairs (e.g., bigrams like "not_good") more effectively.

Q6: How do DistilBERT and RoBERTa differ from traditional TF-IDF models?
A6: TF-IDF treats text as an unordered "bag of words" based on term frequencies. Transformers use
    multi-head self-attention mechanisms to generate deep contextual word embeddings, capturing word
    order, subtle syntactic dependencies, and polysemy (words having different meanings in different contexts).

Q7: What is Aspect-Based Sentiment Analysis (ABSA) and why is it needed?
A7: A single review often contains multiple conflicting opinions (e.g., "The camera is excellent, but
    the battery life is disappointing"). Traditional classifiers average the signals and output an
    ambiguous neutral score. ABSA segments clauses along discourse markers ("but") and assigns separate
    sentiment scores to individual entities ("camera" -> positive, "battery life" -> negative).

Q8: How does Apache Flink handle real-time streaming compared to Spark Streaming?
A8: Apache Flink is a true event-driven stream processor that processes events record-by-record with
    native event-time watermarking. Spark Streaming (in standard micro-batch mode) discretizes streams into
    small batches. Flink achieves lower latency (sub-second) for continuous streaming analytics.

Q9: How is Elasticsearch integrated into this architecture?
A9: Elasticsearch provides distributed full-text indexing using an inverted index. We defined a tailored
    schema mapping with nested properties for ABSA entities. This allows users to perform sub-second
    searches across millions of tweets and filter simultaneously by sentiment, date, and aspect target.

Q10: What role does Apache Airflow play in this system?
A10: Airflow orchestrates the end-to-end data pipeline across 7 discrete stages (Ingest -> Clean ->
     Predict -> ABSA -> Index -> Report -> Log). It provides dependency management, task retries,
     audit logging, and failure isolation.

Q11: How does your system handle offline external dependencies (MongoDB, Elasticsearch)?
A11: The system incorporates defensive health-check wrappers with short timeouts (e.g., 1.5 seconds).
     If MongoDB or Elasticsearch is offline, the code automatically activates resilient local fallbacks
     (SQLite for NoSQL, JSONL files for Elasticsearch), ensuring zero crashes during live demonstrations.

Q12: Why did you use DistilBERT instead of full BERT-Large?
A12: DistilBERT retains 97% of BERT's language understanding while being 40% smaller (66M vs 340M parameters)
     and 60% faster. This allows the model to run efficiently on standard laptop CPUs without requiring an
     expensive dedicated CUDA GPU.

Q13: What is the purpose of the in-memory MapReduce engine in `src/big_data/`?
A13: It serves as a pedagogical and architectural simulation demonstrating how Hadoop MapReduce works
     under the hood: splitting data chunks, running parallel multi-threaded mappers, applying combiners,
     executing hash-partitioned shuffle and sort, and aggregating in reducers.

Q14: What metrics did you prioritize during evaluation and why?
A14: We prioritized Macro F1-score and ROC-AUC over simple accuracy. Simple accuracy can be misleading on
     imbalanced datasets (e.g., US Airlines is 63% negative). Macro F1-score equally weights precision and
     recall across all classes, ensuring the model does not achieve high accuracy by simply guessing the
     majority class.

Q15: How can a student run and demonstrate this project right now?
A15: Open PowerShell in the project directory and execute:
     1. `.venv\Scripts\python.exe -m streamlit run app.py` (opens UI at http://localhost:8501)
     2. `.venv\Scripts\python.exe -m pytest tests/ -v` (runs all 40 unit tests)
     3. `.venv\Scripts\python.exe -m src.streaming.flink_pipeline --records 10` (runs Flink stream)
     4. `.venv\Scripts\python.exe -m src.orchestration.pipeline_tasks --sample-size 25` (runs Airflow DAG)

15. SYSTEM LIMITATIONS & FUTURE SCOPE
====================================================================================================

Current Limitations:
1. Hardware Bound: Transformer models run in CPU mode (`torch.device('cpu')`). While fast enough for
   interactive single-tweet inference (~25-45 ms), real-time processing of the full Twitter firehose
   (10,000+ tweets/sec) requires multi-GPU clusters (e.g., NVIDIA A100/H100 with TensorRT).
2. Operating System Disparities: Apache Flink and Apache Airflow are designed natively for Linux/UNIX
   environments. On Windows, they require WSL2 (Windows Subsystem for Linux) or Docker containers for
   multi-node cluster operation. The project provides verified standalone simulators to bridge this gap.
3. Complex Sarcasm: Sarcastic social media posts without explicit negation tokens (e.g., "Oh great,
   another 4-hour delay, just what I needed!") remain difficult for rule-based and shallow ML models,
   though transformers handle them significantly better.

Future Scope:
1. Cloud Deployment: Containerize all components using Docker Compose and deploy to Kubernetes (EKS/GKE)
   with Helm charts for auto-scaling.
2. Fine-Tuning LLMs: Perform Parameter-Efficient Fine-Tuning (PEFT / LoRA) on open-source LLMs (like
   Llama 3 or Mistral 7B) specifically for social media sarcasm and multi-lingual sentiment.
3. Live Kafka Firehose: Connect an Apache Kafka distributed event bus to ingest live tweets directly
   from the official Twitter/X Developer API v2.
4. Neo4j Knowledge Graph: Link user handles, mentions, and retweets in a graph database to perform
   social network community detection and influencer sentiment tracking.
